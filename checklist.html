Buyer's checklist

The questions a security team asks before it lets an AI agent triage its alerts. Each answer points to the view that shows it, the code that does it and the test that proves it.

Q01. Can it change anything in my environment?

No. Its tools only read the event store, its recommended actions are text, and an approval is a dry run written to approvals.jsonl; no code path sends or executes an action.

Q02. Can a planted instruction in a log redirect it?

The data holds 6 planted texts that ask an AI reader to close or approve an alert; the agent reported all 6 and escalated those alerts to a person. The checker flags any instruction-shaped text the agent saw and did not report.

Q03. Does every claim cite a real event?

Code checks every claim: the cited event must exist, a tool must have returned it to the agent, and each quote must be in the named field. On the recorded run it found 0 unsupported claims in 86.

Q05. Can the record be edited afterwards?

Not without it showing: each audit line carries the hash of the line before, and asa audit verify re-hashes the transcript, verdict, check, approvals and intel files. One changed byte fails at the line it touches.

Q07. What does an alert cost, and what stops a runaway bill?

On the recorded run an alert cost $0.048 on average and $0.102 at most. A live run needs a hard --budget: the worst-case cost of each request is booked before it is sent, and the run stops when the next one could go over.

Q09. What happens when it is unsure?

It answers needs_human and a person decides; a run that ends without a verdict becomes needs_human too. It over-escalates: 20 needs_human answers where the key expects 10.

Q10. What data leaves my network?

In a live run, the alert and the tool results go to the model API through one client with a fixed address. A replay, the checker, the trust report and the audit trail make no network call.
